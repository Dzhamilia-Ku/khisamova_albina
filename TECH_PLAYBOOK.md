# Технический промт: сайт-визитка на Vercel + Yandex Object Storage

Собрано по опыту настройки khisamovaalbina.vercel.app / albinamakeup.ru.
Вставляй в новый чат при старте похожего проекта — описывает инфраструктуру,
паттерны и грабли, не дизайн.

## Стек

- Статический HTML/CSS/JS сайт (без сборки, без npm/package.json) + serverless-функции на Vercel (Node.js, `api/*.js`, автоматическая компиляция ESM→CommonJS).
- Хранилище данных: Yandex Object Storage (S3-совместимое), без БД.
- Домен: регистратор (reg.ru) → неймсерверы переключены на `ns1/ns2.vercel-dns.com` → домен добавлен в Vercel-проект.

## Деплой — стандартный цикл на каждое изменение

1. Правка файла.
2. Локальная проверка перед деплоем: `python3 -m http.server <порт>` в папке проекта + Playwright (`browser_navigate` на `localhost:<порт>`, `browser_resize` под мобильный и десктоп, скриншоты). Не деплоить вслепую.
3. `git add` конкретных файлов (не `-A`), осмысленный commit-message на английском, объясняющий **зачем**, не только что.
4. `git push origin main`.
5. `vercel --prod` — деплоит и алиасит на прод-домен одной командой.
6. Проверка на реальном проде (curl/Playwright), не только "задеплоилось без ошибок".

Похожий цикл нужен, даже если правишь только `api/*.js` —serverless-функции нельзя проверить локальным `http.server` (он не выполняет их), поэтому либо деплоить и тестировать через `curl` на проде/preview, либо временно добавлять диагностическую ветку в саму функцию (см. ниже).

## Секреты и переменные окружения — жёсткое правило

- Никогда не печатать значения токенов/паролей/ключей в чат или в вывод команд.
- Если нужно взять секрет из локального файла — читать программно (Python) и передавать напрямую в команду через shell-переменную, а не через `cat`/`echo` в текст команды:
  ```
  VAL=$(python3 -c "print(open('path').read().strip())")
  vercel env add NAME production --value "$VAL"
  unset VAL
  ```
- `vercel env add NAME production --value "$VAL" --yes` создаёт переменную как **Sensitive** — такие переменные **нельзя прочитать обратно** ни через `vercel env pull`, ни через дашборд, только использовать в рантайме. Если значение понадобится ещё раз (например, для одноразового скрипта очистки) — либо генерировать новое, либо временно завести отдельный не-sensitive способ передачи.
- Перед вставкой значения из файла с нестандартной кодировкой — сначала проверить структуру (`python3` с `encoding='cp1251'`/`utf-8`, смотреть длины строк), а не сразу `cat`/`xxd`/`sed` — обычные unix-тулы бьют по `\n`, а файл может использовать только `\r` (старый Mac-стиль) или другую кодировку, из-за чего можно случайно вывести секрет в терминал при попытке отладки формата.
- Если секрет всё же случайно "засветился" в выводе — сразу сказать об этом пользователю и предложить ротацию ключа, не молчать и не продолжать как ни в чём не бывало.

## Yandex Object Storage — интеграция и грабли

- Работа идёт напрямую через REST API с ручной подписью **AWS SigV4** (Yandex Object Storage S3-совместим) — не нужен npm-пакет aws-sdk, всё на встроенном `crypto`. Регион для подписи: `ru-central1`, сервис: `s3`, хост: `storage.yandexcloud.net`.
- Бакет должен быть **приватным** с самого начала (снять публичный ACL) — если делаете это на существующем публичном бакете, проверьте, что уже успело "утечь", прежде чем продолжать.
- Сервисному аккаунту нужна роль `storage.editor` (или `storage.uploader` для только записи) — **на бакет напрямую** (вкладка бакета «Права доступа» → «Назначить роль»), а не только на папку/каталог — так надёжнее.
- **Главная засада:** если у бакета включено шифрование по умолчанию (SSE/KMS), запись (`PUT`) будет падать с `403 AccessDenied`, а чтение (`GET`) при этом продолжает работать — потому что сервисному аккаунту не хватает прав на сам KMS-ключ. Диагностика: сделать GET с настоящими правами (должен пройти), GET с заведомо неверной подписью (должен вернуть `SignatureDoesNotMatch`, не `AccessDenied` — это подтверждает, что подпись вообще проверяется), и PUT с настоящими правами. Если GET проходит, а PUT — `AccessDenied` при валидной подписи — почти всегда шифрование бакета. Проще всего — отключить шифрование в настройках бакета.
- Данные пишите **отдельным объектом на каждую запись** (например `leads/<ISO-время>-<id>.json`), а не одним растущим файлом — одиночный файл требует read-modify-write при каждой записи и ловит гонки при параллельных запросах.
- Для отладки серверной функции без доступа к логам в реальном времени — временно добавить в неё диагностическую ветку (например `if (req.query.diag === '1') {...}`), задеплоить, curl'ом дёрнуть, посмотреть ответ, затем **обязательно убрать** и передеплоить чистую версию. Не оставлять отладочные эндпоинты в проде.
- Для служебной очистки/массовых операций (list+delete через `ListObjectsV2`) в подписи S3-запроса не забывайте про URL-кодирование и сортировку query-параметров по алфавиту — иначе Yandex вернёт `AuthorizationQueryParametersError`.

## Админ-панель без базы данных

Паттерн, который сработал: пароль + подписанная cookie, без хранения сессий.

- `api/admin-login.js`: сравнение пароля с `ADMIN_PASSWORD` через `crypto.timingSafeEqual` (защита от timing-атак), при успехе — cookie `admin_session=<expiry>.<hmac(expiry, ADMIN_SESSION_SECRET)>`, `HttpOnly; Secure; SameSite=Strict`.
- `api/admin-*.js`: на каждый запрос — пересчитать HMAC от `expiry` и сравнить с cookie (`timingSafeEqual`), проверить `Date.now() < expiry`. Никакого server-side хранилища сессий не нужно.
- Страница админки — `<meta name="robots" content="noindex, nofollow">`, чтобы не попала в поисковую выдачу.
- Удаление в интерфейсе = реальный `DELETE` в хранилище, не мягкое скрытие в UI — проверять после перезагрузки страницы, что запись не вернулась.
- Экспорт в Excel без зависимостей: CSV с UTF-8 BOM (`'﻿' + content`) и `;` как разделителем — открывается в Excel с кириллицей без танцев с библиотеками. Не тащить SheetJS/подобное на страницу с чужими персональными данными без необходимости — лишняя внешняя зависимость на странице с PII.

## Валидация форм

- Email: одной проверкой на `type="email"` не обойтись — браузерная валидация по умолчанию не требует точку в домене и пропускает домены без TLD. Через `input.setCustomValidity(...)` + `input.checkValidity()` можно завести свою логику, не ломая существующий флоу валидации (единая точка входа для всех полей формы).
- Отдельно от формата — список типичных опечаток в популярных доменах (`gmail.ru`, `gmial.com`, `yandex.r` и т.п.) сравнением по точному списку, не фаззи-эвристикой (предсказуемее и меньше ложных срабатываний). Осторожно с доменами, которые выглядят как "опечатка", но реально существуют (`yandex.com`, `mail.com`) — не блокировать их бездумно по чужому списку, сверяться головой.
- Телефон: `pattern` на `type="tel"` (у него нет встроенной проверки формата вообще) — `+7` или `8` + 10 цифр, разделители необязательны.
- Жёсткая блокировка отправки vs мягкая подсказка — разные тексты ошибок, разное поведение; уточнять у заказчика, что нужно, а не выбирать самостоятельно за него для чувствительных полей типа email/телефон.

## Типографика (RU-текст)

Правила, которые реально используются в разметке этого сайта — соблюдать при добавлении/правке любого текста:

- **Неразрывный пробел (`&nbsp;`)** — ставится сразу после короткого предлога/союза (в, на, с, за, но, и, о, к и т.п.), приклеивая его к следующему слову, чтобы он не остался один в конце строки. Пример из кода: `на&nbsp;Вашем лице`, `с&nbsp;опытом работы`. Также используется между числом/инициалом и словом (`11&nbsp;лет`).
- **Неразрывный дефис (`‑`, U+2011, не обычный `-`)** — в составных словах через дефис, чтобы браузер не переносил строку прямо по дефису: `мастер‑классы`, `Бьюти‑эксперт`. Обычный `-` для этого не годится — по нему перенос происходит свободно.
- **Длинное тире (`—`)** для тире в предложении (тире-пауза, тире перед пояснением), не короткий дефис `-`.
- **Кавычки-«ёлочки» (`«…»`)**, не прямые `"…"`, для названий и цитат в русском тексте.
- Если добавляешь новый абзац/пункт — пройтись по нему и расставить `&nbsp;` у всех коротких предлогов/союзов вручную, автоматической расстановки в проекте нет.

## Точечные CSS-правки по запросу клиента ("на 0,5 см", "на 1,5 см ниже")

- Клиент в этом проекте формулирует правки в физических величинах ("подвинь на 0,5 см", "срежь снизу на 1,5 см") — рабочий паттерн: использовать CSS `cm` **как условную, но стабильную единицу для относительной правки** внутри `calc()`, а не как попытку добиться реальной физической точности (реальная физическая точность на экране невозможна, см. ниже). Пример из кода: `padding-top: calc(19px + 0.5cm)`, `height: calc(max(560px, 47.25vw) - 1.5cm)`. Смысл: браузер трактует `1cm` детерминированно как `96px / 2.54 ≈ 37.8px` **всегда одинаково**, поэтому такая правка воспроизводима и предсказуема между правками, даже если не совпадает с реальной линейкой на экране пользователя.
- Не путать с строкой ниже про `mm`/`in`/`cm` — там речь о том, что нельзя обещать клиенту "это будет ровно 5мм на его экране"; здесь — что `cm` внутри `calc()` это ок как удобная единица относительного сдвига, раз уж клиент мыслит в них.

## Адаптивные фотографии через `object-fit: cover` — обрезка "плывёт" по ширине экрана

Заняло целую сессию отладки на живом клиенте — стоит того, чтобы не повторять.

- **Суть проблемы:** контейнер вида "половина вьюпорта по ширине (`50vw`) × фиксированная высота в px" (частый паттерн для фото рядом с текстом) заставляет `object-fit: cover` обрезать **сильнее** по мере роста ширины экрана — потому что ширина контейнера растёт линейно с вьюпортом, а высота стоит на месте. На узком экране почти не обрезается, на широком (1920px+) может срезать пол-лица. Проверка на одной ширине экрана (например, 1440px у разработчика) не ловит баг — нужно проверять весь диапазон.
- **Фикс:** если в кадре есть конкретная область, которую нельзя обрезать (лицо, лого) — привязать высоту контейнера к ширине вьюпорта формулой `height: max(<базовая-высота>px, <N>vw)`, где `N` подобран так, чтобы аспект контейнера (`width/height`) никогда не превышал аспект самого изображения. Тогда объект всегда "упирается" high, а обрезка (если есть) уходит только в боковые поля — безопасное направление.
    - `N` считается так: нужный аспект контейнера `R = imgW / imgH` (аспект самого — уже обрезанного под нужный кадр — файла). Контейнер шириной `0.5·vw` (для схемы 50/50) должен иметь высоту `0.5·vw / R`, то есть `N = 50 / R` (в единицах `vw`).
    - Если после обрезки фото под нужный кадр его аспект **отличается** от аспекта контейнера "по умолчанию" — недостаточно просто поправить `object-position`, надо пересчитать саму формулу высоты под новый аспект, иначе на широких экранах обрезка вернётся.
- **Второй, независимый баг того же угла:** если фото-колонка стоит в CSS Grid рядом с текстовой колонкой (`grid-template-columns`), а высота секции задана только на внешнем `overflow: hidden` контейнере — сама grid-строка по умолчанию тянется под контент (`grid-template-rows: auto`) и может стать **выше**, чем заданная высота секции, если текст в соседней колонке переносится на другую высоту при узких ширинах. Внешний `overflow:hidden` в этом случае молча обрезает низ фото на лишние 20-30px, что незаметно на глаз, но ловится замером `getBoundingClientRect()`. Фикс — явно задать `grid-template-rows` тем же значением, что и высота секции, а не полагаться на `height: 100%` дочерних элементов.
- **Надёжный способ протестировать много ширин экрана без реальных ресайзов окна:** `resize_window` в браузерных инструментах может вести себя нестабильно на Retina/HiDPI (путает физические и CSS-пиксели, иногда игнорирует запрошенный размер). Надёжнее — создать на странице `<iframe>` с точным `width`/`height` в px, указывающий на тот же самый URL (same-origin): `vw`/`vh` внутри iframe считаются от размеров самого iframe, а не окна браузера, так что это даёт точный контроль над "вьюпортом" для теста на любой ширине, включая недостижимые для реального окна разработчика (напр. 1920px на экране 1440px).

## Мобильная адаптация — типичные грабли

- `position: sticky` на шапке для мобильной версии часто не нужен (и не ожидается пользователем) — на десктопе ок, на мобильном лучше `position: static` в мобильном медиа-запросе.
- Верхний экран (hero) с фиксированной `aspect-ratio` без потолка по высоте может оказаться **выше видимой области**, особенно когда браузерный chrome (адресная строка/тулбар) разворачивается на весь размер — контент типа CTA-кнопки уезжает за пределы экрана без скролла. Чинится через `max-height: calc(100svh - <высота шапки>)` — именно `svh` (small viewport height = худший случай, когда весь chrome развёрнут), не обычный `vh`.
- Высота шапки может варьироваться (перенос текста на 1-2 строки в зависимости от ширины) — не хардкодить магическое число в px, а измерять реальную высоту через JS в `--header-h` CSS-переменную на load/resize/orientationchange, с фолбэком в `calc()`.
- Проверять на нескольких размерах вьюпорта, включая короткие/тесные (320×480, 375×667), а не только на одном "типичном" телефоне.
- CSS-единицы `mm`/`in`/`cm` **не соответствуют физическим миллиметрам** на реальных экранах (условность браузеров "1 дюйм = 96px", а не настоящая плотность пикселей устройства) — не использовать их для "оставить отступ в N мм", там нужны обычные px/vh с пониманием, откуда берётся реальная проблема.

## Общая дисциплина

- Перед тем как сказать "готово" — реально протестировать на живом сайте (curl / Playwright), а не только "задеплоилось без ошибок сборки".
- При любой правке, которая может задеть другую часть сайта (десктоп при правке мобильной версии, другие разделы при правке одного) — явно проверить скриншотом, что остальное не сломалось.
- Если в процессе диагностики нужно временно менять код прод-функции (диагностические ветки, отладочный вывод) — обязательно откатывать до чистого состояния и передеплоивать перед тем, как считать задачу закрытой.
- Если локальный файл уже правильный, но клиент видит на сайте старое поведение — **сначала проверить, что реально отдаёт прод** (`curl` живого домена, сравнить с локальным по ключевым CSS-значениям/`grep`), а не сразу считать, что не задеплоено. Бывает и обратное: правка задеплоена и прод отдаёт верный HTML, а клиент смотрит в старую вкладку/автодополнение адресной строки подставило не тот адрес (напр. случайно открылся `localhost:...` вместо боевого домена) — в такой ситуации попросить скриншот **с видимой адресной строкой**, это быстрее любых догадок про кэш.
- `x-vercel-cache: HIT` в заголовках ответа — это не проблема сама по себе (значит отдаётся из edge-кэша), сверять надо `etag`/`last-modified` с временем последнего деплоя и реальным содержимым (`grep` по ключевой строке), а не бояться самого факта `HIT`.
